# Инженерный контекст «Дом Домыч»

Этот файл — краткая карта решений для будущих AI-агентов. Он не заменяет спецификации: перед изменением модуля прочитайте соответствующий первоисточник. По состоянию на 25.09.2026 проект находится на стадии проектирования; описанные ниже компоненты не означают, что приложение уже реализовано.

## Обязательные рамки

Продукт — бот MAX для общего домового чата и личных сообщений, работающий в мобильной и веб-версии. Мини-приложение не входит в MVP. Основной цикл должен пройти от сообщения жителя через подтверждения и обращение до фактической проверки результата. MAX, реестр, официальные государственные действия и исполнитель моделируются там, где нет реальной интеграции; demo-режим и документы должны явно это показывать.

Ключевые продуктовые правила: один подтверждённый житель — один голос; площадь квартиры не влияет на голос. Аудитория выбирается по подтверждённому реестру и scope дела, персональные ответы не раскрываются в общем чате. Повтор сообщения не создаёт новый голос, молчание не равно отрицательному ответу, недоставка не меняет знаменатель. Для обычной проблемы действует порог либо ожидание до пяти часов с последующим запросом доказательств при недостатке поддержки. Авария идёт без ожидания коллективного порога. Ответ «исполнитель отметил выполненным» не закрывает дело без проверки жителями. Неутверждённые пороги — demo policy, а не нормативное требование. Протокол позиции жителей не является официальным протоколом ОСС.

## Стек и степень определённости

Выбран целевой стек: Python 3.13, `asyncio`, `uv`, один пакет `src/dom_domych`; FastAPI/Uvicorn для webhook и health endpoints; Pydantic 2 для внешних DTO и tool schemas; HTTPX AsyncClient для официального Bot API MAX и inference; PostgreSQL 17, SQLAlchemy 2 async/asyncpg и Alembic; PostgreSQL FTS + pgvector; собственный небольшой async agent runtime; PostgreSQL inbox/outbox/jobs; постоянное файловое хранилище; ReportLab/Platypus для PDF; structlog, pytest/pytest-asyncio, Ruff и mypy; Docker Compose и Caddy.

Зависимости и версии фиксируются в проектной конфигурации при создании окружения. Не вводить другой ORM, брокер или agent framework без конкретной необходимости. Новая зависимость должна иметь подходящую открытую лицензию и быть отражена в lockfile и документации.

Модель **не зафиксирована окончательно**. Начальные кандидаты — Qwen3-8B-GGUF (исходный вариант Q4_K_M) для текста/tools и Qwen3-Embedding-0.6B-GGUF для embeddings; inference-контур — llama.cpp/llama-server. Выбор зависит от проверки лицензий, доступного железа, корректности русского tool calling, качества evals и измерений задержки/памяти/нагрузки. Все обращения к модели проходят через `LlmPort`, чтобы кандидат можно было заменить без изменения домена. Эти кандидаты не являются подтверждённым рабочим стендом.

Подробности и лицензии: [01 — объём и стек](../docs/engineering/01-scope-and-stack.md).

## Слои и исполнение

Направление зависимостей: transport/entrypoints → execution/application → domain; infrastructure реализует порты, composition root связывает реализации. Transport нормализует MAX Update и callback, но не считает голоса. Application содержит use cases; domain задаёт права, инварианты, переходы и пороги, не импортируя FastAPI, HTTPX, SQLAlchemy или LLM. Infrastructure содержит PostgreSQL, MAX/inference adapters, поиск, FileStore, PDF и DemoExecutor. Controllers, callbacks и agent tools должны вызывать один и тот же use case.

Целевая схема — модульный монолит с отдельными entrypoints API ingress, worker и scheduler (scheduler/outbox допускается объединить с worker на небольшом стенде). Ingress сохраняет входящее событие в durable inbox и отвечает после надёжной записи. Worker получает событие с истекающей lease, запускает handler или agent run. Сетевые вызовы и inference идут вне SQL-транзакций; write use case выполняет короткую транзакцию. Намерение внешней доставки записывается в outbox в той же транзакции, а отправляет его отдельный worker. Ожидание ответа/срока сохраняется как continuation/job; новое событие запускает обработку на актуальном состоянии.

На конкурентную задачу/use case приходится отдельная SQLAlchemy AsyncSession и Unit of Work с явными commit/rollback. Для изменений применяются уникальные ограничения, idempotency keys и `expectedVersion`; после конфликта версии состояние перечитывают. Долгие jobs и сроки хранятся в PostgreSQL, а не в памяти процесса. Внешняя доставка не считается exactly-once: неизвестный исход обозначается `delivery_unknown`, повторы ограничены. Время — timezone-aware UTC через injected Clock; ускорение demo-времени явно маркируется. PDF рендерится вне event loop по неизменяемому сериализуемому snapshot.

Архитектура и целевая структура: [02 — архитектура](../docs/engineering/02-architecture.md).

## MAX и tools агента

MAX-интеграция строится на официальном HTTPS Bot API и нашем тонком `MaxApiClient` на HTTPX. Вход — FastAPI webhook за Caddy; production использует webhook, polling допустим только как отдельный dev/test режим без активного webhook и с одним consumer на токен. Форматы и методы сверяются с актуальными [официальными docs MAX](https://dev.max.ru/docs) и [Bot API/OpenAPI](https://dev.max.ru/docs-api); не придумывать поля, методы или ограничения. Тестовый групповой чат требует прав бота, личные уведомления — доступного личного диалога. Фактический доступ команды к созданию бота, тестовому чату и inference нужно подтвердить в S0.

Соблюдать документированные лимиты и ответы API: ограничение сообщений на диалог и общий RPS, отдельное ограничение callback; HTTP 200 само по себе не подтверждает успех — проверяется тело результата. Файлы проходят upload URL → загрузка → token → attachment, с ограниченным retry для `attachment.not.ready`. Вложения проверяются по допустимому источнику, размеру и MIME. MAX credentials не переносятся на произвольный upload host или redirect; TLS verification не отключается. Таймаут отправки может дать неизвестный результат, поэтому бездумная повторная отправка запрещена. Актуальные подробности: [03 — MAX integration](../docs/engineering/03-max-integration.md) и [сводка платформы](../docs/platform-max.md).

LLM понимает сообщения, собирает контекст, ищет знания и предлагает маршрут. Она вызывает только allowlist типизированных tools, описанных Pydantic schema и обслуживаемых async handlers через `LocalToolTransport`. Возможный HTTP transport вызывает тот же registry и не является API MAX. Для каждого tool заданы режим, эффект, capabilities и handler. TrustedContext (дом, actor, principal, права, correlation/deadline, demo/live) приходит из проверенного события, а не из аргументов модели. Нет произвольного SQL, shell, HTTP или чтения файлов. Callback-голос фиксирует backend по реальному actor; `poll.answer` не предоставляется LLM. Подсчёт, разрешённые переходы и подтверждение фактического исполнения остаются за backend. Агент сообщает об успехе только после успешного результата handler/адаптера.

Контекст сообщений и документов считается недоверенными данными: инструкции внутри них не меняют полномочия. Важные действия записывают source refs, версии и результат; в audit сохраняется краткое основание и источники, не скрытая цепочка рассуждений. При неизвестных данных агент уточняет, а не угадывает. Дедупликация сочетает scoped retrieval, смысловую оценку и повторную транзакционную проверку кандидатов; embedding score сам по себе не доказывает совпадение.

Подробности: [04 — агент и инструменты](../docs/engineering/04-agent-and-tools.md).

## Данные, приватность и надёжность

PostgreSQL — источник состояния и истории. Доменная модель связывает дома, подтверждённые проживания, квартиры, подъезды, этажи и явные связи инженерных стояков. Стояк нельзя выводить по номеру квартиры. Общий `case` поддерживает проблемы и инициативы с версиями и событиями; опросы хранят снимок правил и аудитории, eligibility отделён от возможности доставки. Ответ уникален для жителя/опроса; повторные callback и сообщения обрабатываются идемпотентно. Порог считается из зафиксированной категории и eligibility, не из числа успешных доставок.

Входящие Update защищаются проверкой секрета и dedupe key. Outbox/jobs используют lease, ограниченные retries, восстановление после падения и dead-letter. Пересечение порога создаёт одно событие. Deadline job перед исполнением перепроверяет состояние/ревизию и становится no-op, если дело уже закрыто. Статус внешней регистрации, workflow дела и результат опроса выполнения хранятся отдельно. История версий, snapshot документа и согласование относятся к конкретной ревизии/hash.

Персональные поля передаются только нужному адресату. В логи, prompts/tool results и Git не попадают токены, пароли и лишние персональные сообщения. Для демо используются синтетические жильцы; реальные интеграции и смоделированные части перечисляются явно. Политика хранения/удаления вложений должна быть определена отдельно, а удаление сообщения фиксируется событием.

Модель данных и переходы: [05 — данные и состояния](../docs/engineering/05-data-and-state.md); процессы и сбои: [06 — сквозные процессы](../docs/engineering/06-runtime-flows.md).

## Ограничения конкурса и внешние зависимости

Использовать публичный документированный MAX API, открытые зависимости и веса с проверенными лицензиями; собственные исходники/contracts входят в сдачу. Секреты хранятся вне Git, логи редактируются. Для публикации отдельно проверяются текущие правила MAX, обработка данных и требования организаторов. Ник бота согласуется до создания, если после создания его нельзя изменить. Реестр жителей, государственные реестры, официальная отправка и внешний исполнитель в MVP моделируются; материалы и карточки должны сообщать об этом. Юридически значимое действие нельзя изображать выполненным на основании генерации PDF или отправки в MAX. После дедлайна сданный commit/tag не передвигается; дальнейшие изменения — отдельно.

Основа этих ограничений: [01 — ограничения и стек](../docs/engineering/01-scope-and-stack.md), [сводка MAX](../docs/platform-max.md), [08 — приёмка и релиз](../docs/engineering/08-verification-and-release.md).

## Три workstream и зависимости

Сначала общий S0: подтвердить доступ к MAX, тестовому чату и inference; согласовать shared contracts/fixtures, границы demo/live, конфигурацию и базовый стенд. Без этого нельзя считать внешние зависимости полученными.

- **A — платформа, MAX и надёжность:** A1 webhook/inbox/стенд → A2 реестр и онбординг → A3 доставка, callbacks, jobs и Clock → A4 восстановление, эксплуатация и mobile/web. A предоставляет события, trusted context, реестр, аудитории, outbox и durable jobs.
- **B — агент, знания, проблемы и аварии:** B1 runtime/tool registry → B2 знания, классификация и retrieval → B3 полный цикл обычной проблемы → B4 аварийный маршрут, сроки и продолжение. B использует контракты A/C и не дублирует бизнес-правила в prompts.
- **C — опросы, инициативы, документы и результат:** C1 аудитории/опросы может начать на fixtures, затем интегрируется с A2/A3; C2 инициативы использует общий tool contract; C3 PDF/карточки зависит от snapshot и фактов B3 и отдаёт результат A3 для отправки; C4 DemoExecutor и проверка выполнения соединяет статусы, повторный опрос и followup B4.

Общие gates: G0 — S0; G1 — реальные MAX-события, retrieval, реестр и опросы (A2+B2+C1); G2 — проблема/инициатива, голоса и PDF в MAX (A3+B3+C2+C3); G3 — авария/исполнение/опрос результата/закрытие или возврат (A4+B4+C4); Release — полная mobile/web-матрица, сбои, лицензии, секреты, demo labels и фиксированная сдаваемая версия. Shared contracts согласуются до параллельных изменений, миграции объединяются в одной истории, уже объединённые revisions не переписываются.

Полный план и владельцы зависимостей: [07 — workstreams](../docs/engineering/07-workstreams.md).

## Проверки и релизные ворота

Целевой CI после появления проекта: `uv sync --locked`, Ruff lint/format, mypy, pytest и применение Alembic migrations на пустой PostgreSQL. HTTP contracts MAX проверяются HTTPX MockTransport, ingress — ASGITransport с lifespan, конкуренция и миграции — на настоящей PostgreSQL (не SQLite). Agent evals на синтетических русских сообщениях проверяют допустимые/запрещённые действия, source refs, неизвестные данные, смешанные случаи, prompt injection и отсутствие выдуманного успеха. Критические правила доступа, голосов, регистрации и закрытия должны проходить полностью; качество модели фиксируется отдельно и с привязкой к revision, quantization, prompt и железу.

Приёмка также требует реального прогона в MAX mobile и web, PDF-визуальной проверки (кириллица, страницы, адреса, snapshot), четырёх сквозных демо-сценариев и сценариев отказа/восстановления. Моки и успешный import не подтверждают работу продукта. Релизный комплект включает lock/config, migrations, синтетические данные, model revisions и лицензии, `.env.example` без секретов, перечень моделируемых частей, инструкции тестового бота и протокол фактически выполненных проверок. Перед сдачей фиксируются commit, tag и SHA-256 архива; submitted tag после дедлайна не меняют.

Критерии полностью описаны в [08 — проверка, демонстрация и фиксация версии](../docs/engineering/08-verification-and-release.md). На момент этой спецификации приложения, тестового набора и подтверждённого стенда нет.
