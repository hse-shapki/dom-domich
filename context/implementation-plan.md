# План реализации: три независимых пула

Статус на 26.09.2026: это **план**; ветки A/K/Z объединены в `main`. A14 process root уже запускает K inbox/scheduler, но Z production repositories/producers, callback/PDF/result wiring и общий G3 отсутствуют. A16 ждёт live MAX, а сквозное приложение ещё не готово. Канонические задачи находятся в трёх файлах: [Алина](tasks-alina.md), [Катерина](tasks-katerina.md), [Замира](tasks-zamira.md). Техническое обоснование — [архитектура](../docs/engineering/02-architecture.md), [данные](../docs/engineering/05-data-and-state.md), [процессы](../docs/engineering/06-runtime-flows.md), [приёмка](../docs/engineering/08-verification-and-release.md). Порядок A/B/C из [07](../docs/engineering/07-workstreams.md) сохраняется; этот план делает его исполнимым по отдельным задачам.

## Владение и параллельность

| Человек / пул | Своя область | Что отдаёт соседям |
|---|---|---|
| **Алина / A** | Python-платформа, MAX, реестр жителей, inbox/outbox/jobs, БД-core, сборка и эксплуатация | Нормализованное событие, доверенный контекст, выборка жильцов, доставка, часы и durable jobs |
| **Катерина / K** | Agent runtime, LLM и знания, дела/дедупликация/evidence, обращения и аварии | Case/Request use cases, события продолжения, проверенные факты и snapshots для документов |
| **Замира / Z** | Аудитории, опросы, инициативы, PDF, DemoExecutor, проверка выполнения | Участники/результаты опросов, документы, события статуса и результата |

Каждый пул можно выполнять параллельно **после фиксации минимального контракта A01/K00/Z00**; ждать всего G0 для доменной работы не требуется. Внешний модуль до его готовности заменяется fake port на синтетических fixtures; готовность отдельного модуля не объявляется готовностью сквозного пути. У каждого task свой ID, владелец, входы и проверяемый результат. Работа внутри пула идёт по указанному порядку, кроме явно независимых задач. Имена участников фиксируют ответственность за ревью и объединение AI-кода, не предполагают ручной набор всего кода.

## Общая граница G0: быстро зафиксировать, затем писать параллельно

1. **A00** создаёт минимальный устанавливаемый каркас. **K00/Z00** одновременно формулируют свои команды, результаты и fake ports, не редактируя общий пакет; предложения передаются Алине для A01.
2. **A01 + K00 + Z00:** зафиксировать только стыки: event envelope, `TrustedContext`, `ToolResult`, базовые IDs/UTC/version, `Clock`, `UnitOfWork`, `HouseContextPort`, `AudiencePort`, `PollPort`, `CasePort`, `RequestPort`, `DeliveryPort`, `JobPort`, `ExecutorPort`, `FileStore`, перечисление событий из [06](../docs/engineering/06-runtime-flows.md). Команды/результаты, ошибки и владельцы схем записаны в коде contracts и короткой таблице интерфейсов. `house_id` и actor приходят из доверенного события, не от модели. После freeze Катерина и Замира могут вести доменные модули до работающего MAX/БД через in-memory adapters.
3. Изменение опубликованного стыка делается отдельной маленькой задачей: обновить контракт, fake, contract test и всех потребителей; версия интерфейса не меняется незаметно в одной ветке. Продакшен-интеграция происходит на G1–G3.

**G0 считается пройденным**, когда проект ставится через lockfile, типизированные contracts и fakes проходят проверки, согласованы fixture дома и demo/live маркировка, а доступ к боту/test chat и inference реально проверен. Если доступ задержан, задачи продолжаются на fixtures, но G0 остаётся открытым с явно записанным блокером live-проверки. Наличие fakes само по себе не доказывает доступ к MAX или модели.

## Правила независимости файлов и данных

- Общие `contracts/`, базовые `domain/ports`, `pyproject.toml`, lockfile, composition root и настройка Alembic — **Алина**; изменение интерфейса сначала обсуждается как отдельный G0/contract change. Бизнес-правила остаются у владельца модуля. Никто не редактирует код соседнего пула для обхода порта.
- Имена модулей внутри `application/`, `domain/`, `infrastructure/postgres/`, `tests/` повторяют владельца. Алина: `residents`, `notifications`, `jobs`, `max` и core persistence. Катерина: `agent`, `knowledge`, `cases`, `evidence`, `requests`. Замира: `audiences`, `polls`, `initiatives`, `documents`, `resolution`, `executor`, `files`. Общий `case` создаёт Катерина; инициатива ссылается на него через `CasePort`, не создаёт второй aggregate.
- Владелец сущности пишет её ORM-модель, repository и tests. Схема PostgreSQL охватывает все сущности из [05](../docs/engineering/05-data-and-state.md); cross-house foreign keys, tenant filters, уникальность, индексы и idempotency проверяются интеграционными тестами на PostgreSQL.
- Каждый пул делает миграции своих таблиц в отдельной непересекающейся revision; Алина проверяет общую историю и добавляет merge revision при параллельных heads. Уже объединённые revisions не переписываются. Если код одной ветки ещё не объединён, другая работает на port/fake, а не импортирует чужую незавершённую ORM-модель.
- На каждую задачу отдельный worktree/ветка или последовательно отдельный commit; в одном рабочем дереве не коммитить чужие изменения. Совместные gates объединяются после проверок контрактов. `context/current-state.md` и статус в `AGENTS.md` меняются по факту реализации, не по этому плану.

| Производитель → потребитель | Независимая разработка до объединения | Реальная связка |
|---|---|---|
| A: `TrustedContext`, `HouseContextPort`, реестр → K и Z | Synthetic house + fake house repository с теми же IDs и eligibility | G1 |
| A: inbox/dispatcher, callbacks, `DeliveryPort`, `JobPort` → K и Z | Event fixtures, fake delivery/job/callback actor; use cases не вызывают MAX напрямую | G1 для callback, G2 для полноценной доставки/таймера |
| K: `CasePort`, факты дела, `RequestPort` → Z | Fixture case/request с version и source refs; Z не пишет вторую таблицу `cases` | G2 для документов, G3 для исполнения |
| Z: `AudiencePort`, `PollPort` → K | In-memory audience/poll с frozen policy и событиями; K не считает голоса | G1 для выборки/ответа, G2 для обычной проблемы |
| Z: `DocumentPort`, `ExecutorPort`, `ResolutionPort` → K | Fake snapshot/status/result; K не приравнивает `done` к `closed` | G2 для PDF, G3 для регистрации и проверки результата |

## Очерёдность интеграции и доказательства

| Gate | Объединяем | Доказательство на стенде |
|---|---|---|
| **G0** | A00–A03, K00–K02, Z00–Z02 | Пакет/lock и contracts, synthetic fixtures, базовые тесты; реальные MAX/LLM probes с записанным результатом |
| **G1** | A04–A10, K03–K06, Z03–Z05 | MAX event → inbox → triage/context; на fixture case реестр → правильная аудитория → уникальный callback-ответ. Защита домов, actor и повторов на PostgreSQL; реальный поиск/создание дела ждёт G2 |
| **G2** | A11, K07–K10, Z06–Z10 | Обычная проблема и инициатива: дедупликация, личные сообщения, голос/таймер/evidence, PDF и карточка в MAX mobile/web |
| **G3** | A12–A14, K11–K14, Z11–Z14 | Авария и оба обычных маршрута: тестовая регистрация, срок/статус, повторный опрос исходной категории, закрытие/возврат |
| **Release** | A15–A17, K15–K16, Z15–Z16 | Четыре [сквозных сценария](../docs/engineering/08-verification-and-release.md), отказы/восстановление, agent evals, все строки MAX mobile/web, визуальная проверка PDF, лицензии/секреты, инструкции и фиксированный commit/tag/архив |

Gate — проверка стыка, а не передача права владеть чужим модулем. Если внешний доступ задержан, задачи на fake/MockTransport продолжаются; live gate остаётся открытым. Нельзя объявить G3 по успешным unit tests или одному сценарию демо.

## Полнота объёма и приоритет

**Обязательный контур:** все A00–A17, K00–K16, Z00–Z16 и gates G0–Release. Он закрывает Python/БД/MAX, пять типов сообщений, агента и tools, знания, дедупликацию, адресные опросы, инициативы, четыре PDF, исполнение, аварии, followup, устойчивость, мобильный и веб-MAX, release package. Значения спорных порогов хранятся как versioned demo policy, пока команда не утвердит их; государственные/УК-интеграции и реестр остаются явно моделируемыми.

**Расширения после сквозного G3:** A18, K17–K19, Z17–Z18. Их можно исследовать раньше на отдельной ветке, но включать в финальный стенд только после проверки основного контура. Нет мини-приложения, платежей, индекса дома и самостоятельной модерации болтовни. Если время ограничено, сокращают расширения, а не последний опрос результата или восстановление после сбоя.

## Как брать задачу

В начале следующей задачи агент уточняет, **кто из Алины, Катерины и Замиры ведёт этот пул**, если это ещё не сказано. Затем выбирает следующий ID из её файла, сверяет зависимости, код и `current-state.md`, пишет реализацию и проверки только для этой задачи и делает один scoped commit. Если человек назвал конкретный task ID, владелец понятен из файла; повторно спрашивать имя не нужно. Переназначение владельца допускается по прямому решению команды и фиксируется в этом плане до работы. Не брать сразу «весь пул» одним AI-запросом.
