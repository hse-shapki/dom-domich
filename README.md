# Дом Домыч

## 1. Назначение решения

«Дом Домыч» — чат-бот в MAX для подтверждённых совершеннолетних жителей многоквартирного дома. Он помогает превратить сообщение о неисправности в понятное дело: определить затронутых жителей, собрать подтверждения, подготовить обращение для ответственной службы и спросить жителей, устранена ли проблема. Бот работает в общем домовом чате и личных сообщениях.

## 2. Основной пользовательский сценарий

Житель сообщает в домовом чате, например, что во втором подъезде нет света. Бот ищет похожее дело, уточняет место при необходимости и предлагает автору запустить опрос. Подходящие жители отвечают лично; в общей карточке показываются только общие числа. После достаточного числа подтверждений автор проверяет текст обращения и выбранную по теме службу, явно согласует и передаёт обращение тестовому исполнителю. Оператор регистрирует его в демо-режиме; автор получает номер и PDF в личном сообщении. Когда оператор отмечает работу выполненной, бот спрашивает исходную группу жителей о результате. По итогам отдельного опроса дело закрывается, возвращается в работу либо остаётся без подтверждённого результата.

## 3. Состав и архитектура решения

| Компонент | Роль |
|---|---|
| Бот MAX и `polling` | Получает сообщения и нажатия кнопок через Bot API MAX. |
| `inbox` и агент | Надёжно сохраняют входящие события, определяют тип сообщения и вызывают типизированные операции с делами, правилами и обращениями. |
| PostgreSQL с pgvector | Хранит тестовый реестр жителей, дела, редакции, опросы, ответы, обращения, события и очереди. |
| `scheduler`, `outbox`, `documents`, `maintenance` | Обрабатывают сроки, доставку сообщений, PDF и очистку данных. |
| FileStore | Хранит загруженные файлы и подготовленные PDF в Docker volume. |
| Локальная команда оператора | Выдаёт коды тестовым жителям, связывает домовой чат и моделирует регистрацию и выполнение обращения. |

`migrate` применяет миграции, `seed` создаёт синтетические данные, `preflight` проверяет БД, MAX и модель. Для основного сценария используется профиль long polling. В Compose есть также отдельный профиль webhook с API и Caddy; он не нужен для описанной ниже проверки.

## 4. Запуск всех локальных компонентов одной командой

После заполнения `.env` и запуска внешнего сервиса модели выполните из корня репозитория:

```bash
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml up -d --build --wait
```

Команда собирает приложение и запускает PostgreSQL, миграции, тестовые данные, проверку готовности и рабочие процессы бота. Она не запускает MAX и Ollama: условия их доступности указаны в разделе 9.

## 5. Необходимые параметры окружения

- Docker с Compose; для запуска из исходного кода отдельно устанавливать Python не требуется.
- Файл `.env`, созданный из [`.env.example`](.env.example). Замените пример пароля, заполните токен бота; пароль в `DATABASE_URL` должен совпадать с `POSTGRES_PASSWORD`, а имя БД — с `POSTGRES_DB`. Рабочие секреты не добавляйте в репозиторий.
- Доступ к тестовому боту MAX и домовому чату, а также MAX-аккаунты проверяющих жителей. Ссылка на бота: **[заполнить перед сдачей]**. Числовой ID тестового чата: **[заполнить перед проверкой]**. Бот должен быть добавлен в чат с правами, необходимыми для сообщений и кнопок.
- Для профиля `polling` у бота не должно быть активного webhook. Для показанного в `.env.example` адреса `host.docker.internal:11434` Ollama должна быть доступна контейнерам с хоста.

## 6. Переменные окружения

| Переменная | Значение для описанного запуска |
|---|---|
| `DATABASE_URL` | URL `postgresql+asyncpg://...@postgres:5432/dom_domych_demo`; имя хоста внутри Compose — `postgres`. |
| `POSTGRES_DB` | `dom_domych_demo`; это имя требуется автоматическому демо-seed. |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL, совпадающий с паролем в `DATABASE_URL`. |
| `MAX_BOT_TOKEN` | Рабочий токен тестового бота; значение предоставляется отдельно и не хранится в Git. |
| `MAX_INGRESS_MODE` | `polling` для команды раздела 4. |
| `LLM_BASE_URL` | Доступный из контейнера адрес модели; для Ollama на хосте в примере — `http://host.docker.internal:11434`. |
| `LLM_MODEL`, `LLM_BACKEND` | В примере — `qwen3:4b` и `ollama`. |
| `LLM_MAX_TOKENS`, `LLM_TIMEOUT_SECONDS`, `LLM_ATTEMPTS` | Настройки вызова модели; значения примера — `512`, `30`, `2`. |
| `PAYLOAD_RETENTION_DAYS` | Срок очистки payload завершённых очередей; в примере — `30`. |
| `MAX_WEBHOOK_SECRET`, `PUBLIC_HOST` | Нужны только для отдельного профиля `webhook`; для `polling` секрет может быть пустым. |

`POSTGRES_USER` в Compose фиксирован как `dom_domych`. `FILE_STORE_DIR` внутри контейнеров фиксирован как `/var/lib/dom-domych/files`. Присутствующие в `.env.example` `PUBLIC_BASE_URL` и `WORKER_ID` текущий Compose-профиль не передаёт приложению.

## 7. Используемые порты

| Порт | Использование |
|---|---|
| `5432/tcp` | PostgreSQL только во внутренней сети Compose; на хост не опубликован. |
| `11434/tcp` | Ollama на хосте в приведённом примере; контейнеры обращаются к ней через `host.docker.internal`. |
| `443/tcp` | Исходящее HTTPS-соединение с Bot API MAX. |
| `8000/tcp`, `80/tcp`, `443/tcp` и `443/udp` | Только для отдельного профиля `webhook`: внутренний API на `8000`, Caddy публикует `80/443` на хост. |

Профиль `polling` не публикует порт приложения или БД на хост.

## 8. Зависимости

Приложение собирается из [Dockerfile](Dockerfile) на Python 3.13; версии библиотек зафиксированы в [`uv.lock`](uv.lock) и описаны в [`pyproject.toml`](pyproject.toml). Основные библиотеки: FastAPI, HTTPX, Pydantic, SQLAlchemy/asyncpg, Alembic и ReportLab. Compose использует образ PostgreSQL 17 с pgvector 0.8.1. Для внешней модели в проверенной конфигурации использовались Ollama 0.32.1 и `qwen3:4b`; модель и её веса в Docker-образ проекта не входят.

## 9. Внешние сервисы и интеграции

| Сервис | Назначение и условия проверки |
|---|---|
| MAX Bot API | Принимает сообщения и кнопки, доставляет личные и групповые сообщения и файлы. Нужны действующий `MAX_BOT_TOKEN`, доступный бот, тестовый чат и аккаунты жителей. MAX нельзя воспроизвести внутри Docker проекта. Доступ к боту: **[заполнить перед сдачей]**. |
| Ollama на хосте | Даёт модели ответы и вызовы инструментов для обработки сообщений. Перед запуском Compose установите Ollama, загрузите `qwen3:4b`, запустите сервис и проверьте доступность адреса `LLM_BASE_URL` из контейнеров. Ollama не входит в текущий Compose, поэтому без неё `preflight` и агентный сценарий не пройдут. |

Прямая отправка в УК, ГИС ЖКХ или другую внешнюю службу не подключена: регистрация и статус исполнителя моделируются локальным демо-оператором.

## 10. Работа с данными

В PostgreSQL сохраняются синтетический реестр домов и проживаний, привязки MAX-аккаунтов, дела, аудитории опросов, ответы, обращения, события и состояния доставки. Аудитория фиксируется на момент открытия опроса: недоставленное личное сообщение не уменьшает число подходящих жителей. В общем чате публикуются агрегаты, а не индивидуальные ответы. PDF и вложения хранятся в FileStore; документы получают снимок данных на момент подготовки. Данные БД и файлов сохраняются в Docker volumes `postgres_data` и `files_data` после остановки контейнеров. Процесс `maintenance` очищает просроченные файлы и удаляет payload завершённых очередей по настройке срока хранения.

## 11. Порядок работы с тестовыми данными

При первом запуске Compose процесс `seed` идемпотентно создаёт два тестовых дома, жителей и синтетические маршруты для освещения, воды, отопления и лифта. В первом доме есть 12 подтверждённых взрослых жителей пятого этажа второго подъезда; часть дополнительных записей проверяет другие категории и ограничения. Seed разрешён для БД `dom_domych_demo` только с явным флагом, который уже указан в Compose. Тестовые записи не означают проверку реального проживания и не содержат настоящих контактов жителей.

Оператор получает `house_id` и `residency_id` нужных тестовых записей из БД. Следующая команда показывает синтетических подтверждённых взрослых жителей пятого этажа второго подъезда первого дома:

```bash
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml exec postgres psql -U dom_domych -d dom_domych_demo -c "SELECT r.house_id, r.id AS residency_id, a.entrance, a.floor FROM residencies r JOIN apartments a ON a.id = r.apartment_id AND a.house_id = r.house_id WHERE r.source = 'demo' AND r.confirmed AND r.adult AND r.valid_until IS NULL AND a.entrance = 2 AND a.floor = 5 ORDER BY r.id"
```

Оператор связывает числовой MAX chat ID с домом и после проверки совершеннолетия выдаёт каждому участнику одноразовый код. Команды выполняются в запущенном контейнере с его `DATABASE_URL`:

```bash
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml exec inbox dom-domych-demo-operator bind-house-chat --house-id HOUSE_UUID --max-chat-id CHAT_ID
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml exec inbox dom-domych-demo-operator issue-invitation --house-id HOUSE_UUID --residency-id RESIDENCY_UUID --adult-verified --ttl-hours 24
```

`HOUSE_UUID`, `RESIDENCY_UUID` и `CHAT_ID` здесь являются заполнителями, а не реальными значениями. Один код нельзя публиковать в общем чате; тестовый житель вводит его в личке боту командой `/start КОД`. Повторный запуск `seed` не перезаписывает существующие записи. Порядок подготовки стенда подробнее описан в [эксплуатационной инструкции](docs/release/platform-operations.md).

## 12. Пошаговая проверка решения

1. Заполните `.env`, обеспечьте доступность MAX и Ollama, затем выполните команду раздела 4. Проверьте журнал `preflight`: БД, MAX и модель должны отвечать; активных webhook в режиме `polling` быть не должно.
2. По разделу 11 привяжите тестовый домовой чат, выдайте коды нескольким синтетическим жителям и введите каждый код в личном MAX. Бот должен подтвердить квартиру. Проверьте сценарий и в MAX web, и в мобильном клиенте.
3. Подтверждённый житель пишет в группу: «Не горит свет на пятом этаже второго подъезда». Автор подтверждает запуск опроса в личке. В группе появляется карточка, а подходящие жители получают личные приглашения.
4. Трое подходящих жителей подтверждают проблему. Сравните общий счётчик, отметку выбора вместо кнопок в личном приглашении и поведение повторного нажатия. Ответ жителя из другой категории не должен прибавить голос.
5. После достижения демо-порога автор в личке выполняет `/prepare ID_ДЕЛА`, проверяет описание и название службы, затем `/approve ID_ОБРАЩЕНИЯ` и `/send ID_ОБРАЩЕНИЯ`. `ID_ОБРАЩЕНИЯ` берётся из ответа бота. Для `ID_ДЕЛА`, если бот его не сообщил, оператор читает последнее дело в тестовой БД: `SELECT id, title, status FROM cases ORDER BY created_at DESC LIMIT 5`. Если правила для темы нет, ожидается просьба уточнить маршрут вместо заявки.
6. Доверенный оператор выполняет `list` для `HOUSE_UUID`, берёт из результата `OPERATION_UUID` и выполняет `register` в контейнере `inbox`. Повтор той же регистрации не должен создать второй номер. Проверьте личный PDF и отсутствие PDF в общем чате.
7. Оператор выполняет `done` для этой операции с один раз выбранным `EVENT_UUID` и при проверке повтора использует тот же UUID. Бот открывает отдельный личный опрос исходной аудитории. После срока опроса ответы жителей определяют итог: подтверждение, возврат дела в работу или неподтверждённый результат. Статус оператора `done` сам по себе дело не закрывает.

Команды оператора для шагов 6–7:

```bash
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml exec inbox python -m dom_domych.entrypoints.zamira_operator list --house-id HOUSE_UUID
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml exec inbox python -m dom_domych.entrypoints.zamira_operator register --house-id HOUSE_UUID --operation-id OPERATION_UUID
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml exec inbox python -m dom_domych.entrypoints.zamira_operator done --house-id HOUSE_UUID --operation-id OPERATION_UUID --event-id EVENT_UUID
```

Команды и ожидания для оператора, а также длительность опроса результата приведены в [ручном сценарии](docs/release/zamira-manual-demo.md). Фактические результаты web/mobile отмечаются в [матрице проверки MAX](docs/release/max-mobile-web-matrix.md); локальные тесты не заменяют такой прогон.

## 13. Примеры ожидаемого поведения

| Действие | Ожидаемое поведение |
|---|---|
| Житель подтверждает проблему | Его ответ учтён один раз; в личке показан выбор, в группе меняется только общий счётчик. |
| Личное приглашение не доставлено | Житель остаётся в числе подходящих для опроса. |
| Сообщение содержит несколько разных неисправностей | Бот просит описать их отдельно, чтобы не выбрать случайную службу. |
| Для темы нет проверенного правила дома | Обращение не готовится; бот просит уточнить проблему или проверить маршрут. |
| Оператор повторяет регистрацию или событие `done` | Второй номер или второй опрос не создаётся. |
| Оператор отметил работу выполненной | Начинается проверка жителями; дело не считается автоматически закрытым. |

## 14. Известные ограничения

На 30.09.2026 код прошёл 319 локальных тестов на чистой PostgreSQL 17, а транспорт MAX и путь с Ollama проверялись отдельно. Полный путь от живого сообщения в MAX через модель, опрос, заявку и проверку результата в одном live-прогоне ещё не подтверждён. Допустимый голос и подготовленные PDF в MAX mobile/web также требуют ручной проверки. Ollama работает вне Compose; при выключенном хосте или модели бот недоступен. Реестр, маршруты служб и номера регистрации являются тестовыми; демо-порог не является нормативным требованием. **[Заполнить после проверки: ссылка на работающего бота и фактические результаты прохождения сценария.]**

## 15. Остановка и повторный запуск

Остановка контейнеров с сохранением данных в volumes:

```bash
docker compose --env-file .env -p dom-domych --profile polling -f deploy/compose.yml down
```

Для повторного запуска выполните команду раздела 4 с тем же `.env`; `seed` не дублирует тестовые записи. Ollama должна продолжать работать на хосте. Команду `down -v` для обычной остановки не используйте: она удаляет volumes с БД и файлами.
