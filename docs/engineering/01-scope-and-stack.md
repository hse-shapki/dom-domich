# 01. Объём, ограничения и технический стек

[Навигация](README.md)

## 1. Целевой объём

Обязательный фундамент: регистрация участника через личный диалог, тестовый подтверждённый реестр, квартира → подъезд / этаж / инженерные стояки, данные ответственных, история событий.

| Блок | Что реализуем |
|---|---|
| Агент | Авария / обычная проблема / вопрос / инициатива / разговор; сбор контекста, уточнения, выбор действий и инструментов |
| Проблемы | Дедупликация по месту, времени и смыслу; одно дело с подтверждениями разных жителей |
| Подтверждения | Адресные личные сообщения; порог от подходящей категории; период ожидания и дополнительные доказательства |
| Инициативы | Карточка в сообщении, позиции жителей, участие и поддержка, адресные напоминания |
| Документы | PDF обращения, протокола опроса/позиции жителей и реестра уведомлений; подготовка жалобы |
| Исполнение | Регистрация в тестовом адаптере, статусы, опрос затронутой категории после выполнения, повторное открытие |
| Аварии | Срочный маршрут, контроль применимого срока, сбор материалов при просрочке |
| Знания | Минимальная база правил и документов, необходимых для обоснованной маршрутизации |

Расширение после сквозной работоспособности: память дома, анализ фото, голос, повторные проблемы, сводки, ранние признаки общей аварии. Базовая модель Qwen3-8B текстовая: понимание фото и аудио требует отдельных адаптеров и моделей, а не просто загрузки файла в чат.

Мини-приложение, React UI, MAX Bridge, платежи, индекс дома и модерация разговоров в эту реализацию не входят. React рекомендован условиями, но не обязателен для бота.

## 2. Матрица ограничений хакатона

Источник требований — текст, предоставленный командой, и [файл трека](../Умный%20город.pdf). Это перевод требований в инженерные действия, не юридическое заключение.

| № | Требование | Решение / доказательство при сдаче |
|---|---|---|
| 1 | Тематика управления домом и обоснование проблемы | Три сценария дома, примеры потерь в переписке, проверяемые метрики; рыночные цифры из IDEA перепроверить перед защитой |
| 2 | Основной сценарий проверяется в MAX | Начало, подтверждение, PDF и проверка результата выполняются в реальном тестовом чате и личке |
| 3 | Работа в мобильной и веб-версии | Отдельная матрица приёмки mobile/web; стандартные сообщения, callback-кнопки, файлы |
| 4 | JS/React рекомендованы, другие языки разрешены | Python backend; интерфейс использует официальный Bot API MAX через HTTPS |
| 5 | Бот либо бот с мини-приложением | Только бот |
| 6 | Собственный API необязателен | Tools по умолчанию являются функциями сервисов; HTTP только по технической необходимости |
| 7 | Нельзя закрытые библиотеки, частные API и чужой несвободный код | Публичный документированный MAX API; открытые зависимости и веса; реестр лицензий; наш исходный код и contracts включены в сдачу |
| 8 | Нельзя рабочие секреты в репозитории | Переменные окружения / файлы secrets вне Git, редактирование логов, проверка истории перед сдачей |
| 9 | Законодательство, правила MAX и хакатона | Проверка правил обработки данных и публикации; для демо синтетические жильцы; проверенные нормативные источники и согласование официального действия |
| 10 | Моделируемые интеграции обозначены | `mode=demo` в данных, маркировка карточек и PDF, список реальных и тестовых частей в материалах |
| 11 | Ник после создания не изменить | Имя/ник согласовать до регистрации; не рассчитывать на переименование |
| 12 | Сданный код после дедлайна не менять | Фиксированный commit/tag, архив и контрольная сумма; новые работы в отдельной ветке |

Внутренний endpoint собственного приложения не является использованием чужого недокументированного API: его реализация и контракт входят в проект. Закрытый облачный LLM не закладываем обязательной зависимостью. Если команда позже выбирает hosted provider, сначала проверяет его допустимость по правилам организаторов; само наличие публичной документации не доказывает соответствие всему пункту 7.

## 3. Выбранный стек

Это рекомендуемая конфигурация проекта. Точные patch-версии фиксируем на S0 после проверки совместимости, вместе с lockfile и image digests. Не устанавливаем произвольные `latest` в сданной версии.

| Участок | Технология | Где и зачем |
|---|---|---|
| Backend | Python 3.13, type hints, `asyncio` | Весь прикладной код; ports через `typing.Protocol`, доменные объекты через dataclasses |
| Проект и зависимости | uv, `pyproject.toml`, `uv.lock`, src layout | Один устанавливаемый пакет `dom_domych`; воспроизводимая установка через `uv sync --locked` |
| MAX | Наш `MaxApiClient` на HTTPX AsyncClient | Только документированные HTTPS-методы Bot API; входящие Update через FastAPI |
| HTTP-сервер | FastAPI + Uvicorn | ASGI webhook за Caddy, health/readiness; optional tools transport |
| Валидация | Pydantic 2 | DTO событий и tools; JSON Schema из моделей; строгая проверка аргументов LLM |
| Хранение | PostgreSQL 17 | Жители, дела, опросы, события, очереди, аудит |
| Доступ к БД | SQLAlchemy 2 async + asyncpg; Alembic | Repositories и Unit of Work; версионируемые миграции; SQL для очередей и поиска |
| Поиск | PostgreSQL full-text + pgvector | Поиск кандидатов и документов: фильтры + текст + embeddings |
| LLM | Qwen3-8B-GGUF, исходный кандидат Q4_K_M | Открытая текстовая модель для русского текста и выбора инструментов; принимается только после evals |
| Inference | llama.cpp / llama-server | Self-hosted inference через документированный HTTP-интерфейс; отдельный процесс, Python-клиент на HTTPX |
| Embeddings | Qwen3-Embedding-0.6B-GGUF | Отдельный процесс embeddings; фиксируем revision, размерность и нормализацию |
| Agent orchestration | Собственный async runtime на Python | Pydantic tools, async handlers, лимит шагов, проверки, сохранение запусков; без обязательного agent framework |
| Jobs | PostgreSQL inbox/outbox/jobs + worker | Lease, retry, dedupe; одна БД вместо дополнительного брокера |
| PDF | Открытый ReportLab, Platypus + разрешённый шрифт с кириллицей | Документы по шаблонам, таблицы/переносы, встроенный шрифт; отдельные PDF jobs |
| Файлы | FileStore interface + persistent volume | Фото и PDF; backend-путь не определяется пользовательским именем файла |
| Логи | structlog + стандартный logging | Структурированные trace/run/case ID, contextvars, редактирование секретов |
| Тесты | pytest + pytest-asyncio; HTTPX MockTransport/ASGITransport | Domain, HTTP contracts, async handlers; транзакции/конкуренция на реальной тестовой PostgreSQL |
| Качество кода | Ruff + mypy | Форматирование, lint и статическая проверка типов в CI |
| Развёртывание | Linux, Docker Engine + Compose, Caddy | Воспроизводимые процессы, HTTPS для webhook; macOS допускается для локальной разработки |

Python 3.13 выбран как целевая ветка проекта, не как утверждение о самой новой версии. Фиксируем patch в `.python-version` и контейнерном образе; совместимость пакетов проверяем на S0. [Python](https://www.python.org/downloads/), [структура uv-проекта](https://docs.astral.sh/uv/concepts/projects/layout/).

MAX предоставляет HTTPS API и OpenAPI-спецификацию, которыми можно пользоваться из Python. Наш тонкий HTTPX-адаптер реализует нужное подмножество методов и остаётся частью открытого исходного кода. Не называем его официальным Python SDK. [Bot API MAX](https://dev.max.ru/docs-api), [HTTPX async](https://www.python-httpx.org/async/).

### Что меняется под Python

- Один пакет с `src/dom_domych`, общим `pyproject.toml` и lockfile; ingress, worker и scheduler — отдельные entrypoints этого пакета.
- Сеть и БД асинхронны. Общие HTTPX clients создаются на lifespan процесса и закрываются при shutdown; MAX, inference и upload используют раздельные настройки авторизации.
- Одна `AsyncSession` на use case/задачу. Параллельные tools не разделяют сессию. Unit of Work явно задаёт commit/rollback; ORM-объекты не уходят в prompts и наружные DTO. [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).
- Durable jobs остаются в PostgreSQL. `FastAPI.BackgroundTasks` и `asyncio.create_task` не заменяют inbox/outbox и сохранённые сроки.
- Синхронная генерация PDF выполняется в отдельной worker-задаче и ограниченном process pool; не блокирует webhook/event loop. Передаём сериализуемый snapshot, а не сессию БД.
- Pydantic генерирует tool schemas; capabilities и переходы по-прежнему проверяет домен. Native tool calling модели и реальная валидация остаются разными проверками. [Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/).
- PostgreSQL, pgvector, llama.cpp, выбранные модели и Caddy сохраняются: смена языка не требует менять их или добавлять Celery/Redis.

### LLM: что проверяем до основной реализации

- На доступной машине загружается конкретный GGUF и работает формат tool calling с выбранным chat template.
- Модель возвращает валидные аргументы и правильно выбирает действие на русском языке.
- Измерены время ответа, память и пропускная способность на нескольких одновременно активных делах.
- Поддержка tools у сервера не гарантирует качество выбранной модели. При провале evals меняем размер/модель внутри `LlmPort`, не переписывая домен.
- Первоначальные run budgets: максимум 8 последовательных tool-шагов и 60 секунд; это настраиваемые инженерные значения для измерения, не нормативы.
- Реальная доступность inference-хоста пока неизвестна. Получение доступа и benchmark — зависимость S0; не обещаем конкретную скорость или расход памяти до измерения.

Источники: [llama.cpp](https://github.com/ggml-org/llama.cpp), [function calling](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md), [модель](https://huggingface.co/Qwen/Qwen3-8B-GGUF), [embeddings](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B-GGUF).

## 5. Моделирование интеграций

| Реально работает | Явно моделируется |
|---|---|
| MAX, доставка событий и сообщений, callback, выдача файлов | Подтверждённый реестр квартир и жильцов |
| Работа LLM, поиск, опросы, подсчёт, документы | Проверка собственности/проживания через государственные источники |
| Состояния дел, таймеры, повторный опрос | Отправка в ГИС ЖКХ, ответ УК, официальный регистрационный номер |

Не выводим из MAX user_id, телефона или Digital ID право проживания. Связь с квартирой устанавливается отдельным процессом и в MVP помечена тестовой. Протокол позиции жителей не маркируется как готовый официальный протокол ОСС.
