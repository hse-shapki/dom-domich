## 1. Проверяемая готовность

Функция считается готовой, когда её можно вызвать через MAX, данные сохраняются, результат соответствует правилам и ошибка не теряет дело. Мок API-транспорта в unit test не доказывает работу в мессенджере.

### Domain / integration — pytest, pytest-asyncio и PostgreSQL

HTTP contracts MAX проверяем через HTTPX MockTransport, FastAPI ingress — через ASGITransport с управляемым lifespan. Конкурентные операции БД проверяем с отдельной AsyncSession на task и реальной PostgreSQL, не SQLite. CI включает `uv sync --locked`, Ruff, mypy, pytest и применение Alembic-миграций на пустой базе.

| Проверка | Ожидаемый результат |
|---|---|
| Двенадцать жителей сообщают об одной проблеме | Одно дело, до двенадцати уникальных подтверждений при подходящей категории |
| Один житель пишет/нажимает двенадцать раз | Один активный ответ, сохранённые источники/ревизии |
| Похожие слова, разные подъезды/объекты | Не объединяются без основания |
| Новая авария после подтверждённого устранения | Новое дело со связью повторяемости, а не потеря истории |
| Пересечение порога двумя одновременными ответами | Одна операция подготовки обращения |
| N=0, дробный порог, недоступная личка | Правильное округление; нет деления на ноль или смены знаменателя |
| Чужой дом, неподходящий actor, устаревшая кнопка | Отказ без изменения данных |
| Ответ на границе deadline | Применена одна документированная политика из 05 |
| Изменение инициативы после голосов | Новая revision, нельзя сохранить старую поддержку молча |
| Статус done без опроса | Дело не закрывается |
| Мало ответов о результате | `resolution_unconfirmed` |
| Отрицательный результат | Возврат и followup |
| Старый job после закрытия | No-op без новой жалобы |
| Падение worker/outbox | Восстановление по lease, идемпотентность внутренней операции |

## 2. Agent evals

Отдельный набор синтетических сообщений на русском. Не копировать только фразы демо. Для каждого примера сохраняем исходный контекст, допустимые действия, запрещённые действия и необходимые source refs.

| Группа | Что оцениваем |
|---|---|
| Классификация | Пять типов, смешанные сообщения, разговор без реакции |
| Неизвестные данные | Агент уточняет дом/этаж/время вместо догадки |
| Дедупликация | Совпадение, противоречие, новое возникновение, несколько проблем в сообщении |
| Маршрутизация | Ответственный и правило подтверждены источниками |
| Evidence | Недостаток поддержки не равен отсутствию проблемы; нет заявления об анализе фото без vision |
| Tools | Валидные аргументы, правильные зависимости вызовов, отсутствие выдуманного успеха |
| Продолжение | Новое событие использует актуальную version, не старый план |
| Недоверенный контент | Фразы «игнорируй правила», чужие IDs, команды внутри документа не меняют права |

Метрики: доля корректных действий по категориям, ложные объединения, пропуски срочных случаев, успешность schema validation, число tool calls, p50/p95 latency. Отдельно фиксируем hardware, model revision, quantization, prompt revision и длину контекста.

Критические сценарии доступа, голосов, фиктивной регистрации и закрытия без подтверждений должны проходить полностью. Для качества LLM команда фиксирует порог принятия на S0 после baseline; низкий результат нельзя скрывать общей средней метрикой.

## 4. Документы

Для обращения, протокола и реестра:

- Числа, адресат и авторство совпадают с snapshot.
- Есть case ID, revision и происхождение данных.
- Видны тестовые интеграции и статус документа.
- Кириллица встроенным шрифтом, переносы длинных адресов, таблицы на нескольких страницах.
- PDF рендерится и просматривается перед приёмкой; отсутствие ошибки генератора не гарантирует читаемость.
- Частные ответы и персональные данные не публикуются всем участникам дома.

## 5. Сценарии показа

1. **Проблема:** жители пишут об освещении → одно дело → личный опрос нужного этажа → порог → обращение → тестовое исполнение → положительная проверка.
2. **Недостаток поддержки:** мало ответов → конец периода → запрос доказательств → новый обоснованный шаг.
3. **Авария:** протечка → срочная заявка → тестовая регистрация → ускоренный явно обозначенный таймер → просрочка → черновик жалобы.
4. **Инициатива:** велопарковка → карточка → позиции → PDF → исполнение → жители сообщают, что не выполнено → возврат.

Во время показа меняем хотя бы одну формулировку и локацию, чтобы проверить работу агента вне заученной реплики. Основной сценарий доступен жюри в самом MAX; видео служит дополнительным материалом.

## 6. Комплект сдачи

- Исходный код и README с точными командами запуска после реализации.
- `pyproject.toml`, `uv.lock`, `.python-version`, Alembic-миграции, синтетические seed data, выбранные model revisions и инструкции получения открытых весов.
- `.env.example` только с названиями и безопасными placeholders; реальные значения вне Git.
- Ссылки на лицензии, перечень зависимостей/весов/шрифтов и необходимые NOTICE.
- Таблица реальных и моделируемых систем; ограничения демо и правила ускоренного времени.
- Доступ к тестовому боту и инструкция прохождения сценариев.
- Протокол проверки mobile/web и сценариев; материалы в формате, требуемом организаторами.

Точные формат подачи, дедлайн и доступ команды к платформе сверяются с организаторами; старые даты/статусы из hackathon.md не считаем актуальным подтверждением регистрации.

## 7. Фиксация релиза

1. Выполнить проверки и зафиксировать выбранные расширения.
2. Проверить Git diff и историю на секреты, лишние персональные данные и несвободные файлы.
3. Создать сдаваемый commit и tag, собрать архив; записать SHA commit и SHA-256 архива.
4. Сохранить модель/шаблоны/prompts/config revisions и image digests, чтобы стенд соответствовал сдаче.
5. После дедлайна не менять переданную версию и не подменять её на стенде. Дальнейшая разработка — отдельная ветка; submitted tag не передвигается.

Сейчас реализованы только чистые правила и выбор аудитории Z с unit/fake tests. Сквозные сценарии, MAX mobile/web, PostgreSQL concurrency и релизные пункты не проверены; текущий статус — в [контексте](../../context/current-state.md).
