# Z-MVP-2: ручная проверка в MAX

Это протокол, **не отметка о прохождении**. Нужны общий стенд A-MVP-1/2, один demo-дом с 12 синтетическими подтверждёнными взрослыми жителями нужной категории, отдельный житель вне категории, автор инициативы и доступ к MAX web и mobile. До начала запишите backend commit, policy revision, время UTC и версии клиентов. Состояние workers и бота проверьте read-only командой `uv run python -m scripts.max_operations probe` и по `docker compose -f deploy/compose.yml ps`; токены и личные сообщения в отчёт не копируйте.

## Голос и карточка

1. Автор пишет в домовом чате о проблеме нужного этажа. Ожидается одна обезличенная карточка с `0/12`; 12 личных приглашений относятся к frozen audience. Один житель с недоступной личкой остаётся в знаменателе.
2. Трое подходящих жителей нажимают «Подтверждаю» на разных устройствах. Каждый видит личное «Голос учтён»; **та же** публичная карточка меняется до `3/12`. Повтор первого не увеличивает число; смена на «Не подтверждаю» уменьшает его до `2/12`, обратная смена возвращает `3/12`.
3. Житель вне категории нажимает кнопку. Голос и знаменатель не меняются, чужие ответы или квартиры в группе не появляются. Проверьте оба клиента MAX и время обновления карточки.
4. Автор создаёт инициативу и затем меняет формулировку командой `/revise` в личке. Новая карточка показывает редакцию 2 и `0/12`, новые личные приглашения относятся только к ней. Старая кнопка даёт сообщение об устаревании без нового голоса. Повтор команды ревизии не создаёт редакцию 3.
5. После окончания опроса по обычному расписанию карточка показывает итог и лишается кнопок. Не меняйте часы или статусы напрямую в live-БД ради показа; для короткого демо используйте заранее начатую инициативу.

## Четыре PDF

Проведите четыре разрешённых сценария из [протокола PDF](zamira-live-pdf-smoke.md): согласованное demo-обращение и доверенная регистрация; итог инициативы; служебный реестр уведомлений с отдельным правом; проверенный deadline и черновик жалобы. Каждый файл должен прийти **только в личку своего адресата**. Откройте и скачайте каждый в MAX web и mobile, сравните адрес, версии, snapshot hash, итоговые числа и маркировку демо; с сохранёнными метаданными FileStore сравните SHA-256 скачанных bytes. В группе не должно быть PDF и внутренних ID жителей. Протокол позиции не содержит персональных ответов; внутренние ID допустимы только в приватном реестре.

Отдельно проверьте повтор обработки события: второй PDF с тем же operation key не создаётся. Если MAX upload или адресат недоступен, зафиксируйте `pending`/`delivery_unknown`/`failed` по факту, не записывайте доставку как успешную. Результаты по каждому клиенту и каждому шаблону внесите в [матрицу](max-mobile-web-matrix.md) с временем UTC, commit и обезличенным evidence.

Локальные автоматические опоры: `tests/infrastructure/test_z05_poll_callback_postgres.py`, `test_z06_initiatives_postgres.py`, `test_z07_cards_outbox.py`, `test_z08_followup_postgres.py`, `test_z10_max_pdf_pipeline.py`, `test_g3_runtime.py`. Они используют PostgreSQL и MAX MockTransport и не заменяют описанный live прогон.
