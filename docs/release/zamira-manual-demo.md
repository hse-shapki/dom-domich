# Z14/Z16: ручной сценарий демо проблемы и проверки результата

Это план live-показа, а не отметка о прохождении G3. Используйте только отдельный `demo=true` дом, 12 синтетических подтверждённых совершеннолетних жителей одной категории и две разные проблемы для позитивного и отрицательного исходов. Прямые изменения live-БД запрещены. `DEMO-*` — номер моделируемого исполнителя, PDF не доказывает отправку в УК.

## Подготовка

1. Зафиксируйте backend commit, версии модели, MAX web/mobile, демо-правил и время UTC. Проверьте готовность `api`, `inbox`, `scheduler`, `outbox`, `documents` и read-only `uv run python -m scripts.max_operations probe`.
2. Через `dom-domych-demo-operator issue-invitation` после проверки взрослых выдайте одноразовые коды каждому демо-жителю; житель активирует их в личном MAX. `bind-house-chat` связывает числовой групповой `chat_id` (он может быть отрицательным). Не публикуйте коды и ID жителей в общем чате.
3. Для темы освещения в этом демо-доме должен быть заранее проверенный scoped источник правила и ответственный. Если агент не находит его, корректный результат — уточнение; подготовка обращения без правила не должна проходить.

## Оба пути: проблема → обращение → PDF

1. Подтверждённый житель пишет в группу: «Не горит свет на пятом этаже второго подъезда». Бот сначала ищет совпадения и лично предлагает автору кнопки «Да, запустить»/«Нет». «Нет» показывает нейтральный popup и закрывает draft; «Да» показывает «Запускаю опрос» и только затем создаёт публичную карточку с демо-порогом и правильной аудиторией `12`. В группу и личку не должны попадать tool trace, внутренние рассуждения или UUID дела.
2. Первый и второй подходящие жители нажимают «Подтверждаю»: MAX показывает всплывающее acknowledgement «Голос учтён», публично `1/12` и `2/12`. Первый повторяет выбор: acknowledgement сообщает «Этот голос уже учтён», счётчик остаётся `2/12`. Первый меняет ответ на «Не подтверждаю»: всплывает «Голос изменён», счётчик `1/12`; возвращает «Подтверждаю»: снова `2/12`. Третий подходящий житель подтверждает: `3/12`. Житель вне frozen audience получает только нейтральное всплывающее предупреждение, голос не появляется. Callback не создаёт отдельное личное сообщение.
3. Порог `demo-problem-v1` — `ceil(20% × 12) = 3`; дело переходит к подготовке обращения. Подтверждённый житель проверяет черновик, правило и адресата, затем явно согласует и отправляет его через доступный агентный маршрут. Если live агент/правило не доводят маршрут до submit, зафиксируйте блокер, не создавайте request вручную.
4. На доверенной operator-консоли найдите operation ID и зарегистрируйте демо-обращение:

   ```bash
   docker compose -f deploy/compose.yml exec api python -m dom_domych.entrypoints.zamira_operator list --house-id <DEMO_HOUSE_UUID>
   docker compose -f deploy/compose.yml exec api python -m dom_domych.entrypoints.zamira_operator register --house-id <DEMO_HOUSE_UUID> --operation-id <OPERATION_UUID>
   ```

   Повтор `register` должен вернуть `emitted=False`. После `request.registered` document worker готовит immutable `appeal-v1`; уполномоченный житель получает PDF только в ЛС. Проверьте демо-номер, ревизии и hash снимка. Общая группа не получает файл.

## Проверка результата: два отдельных дела

1. Для каждого зарегистрированного дела доверенный оператор запускает `done` с заранее созданным UUID события; повторите **с тем же** `event-id` и проверьте `emitted=False`:

   ```bash
   docker compose -f deploy/compose.yml exec api python -m dom_domych.entrypoints.zamira_operator done --house-id <DEMO_HOUSE_UUID> --operation-id <OPERATION_UUID> --event-id <EVENT_UUID>
   ```

   Статус исполнителя `done` открывает отдельный личный опрос **исходных** 12 жителей и оставляет дело `checking_resolution`.
2. **Позитивное дело:** 12 исходных жителей отвечают «да». После финализации `demo-resolution-v1` ожидается `closed` (`12/12` ответили, `12/12` «да», `0/12` «нет»).
3. **Негативное дело:** три исходных жителя отвечают «нет», остальные девять — «да». После финализации ожидается `reopened`: `3/12 = 25%` отрицательных ответов среди ответивших, что строго больше демо-порога `20%`. Отрицательный исход имеет приоритет.
4. Текущий runtime финализирует опрос результата **по истечении двух часов** и после дренажа predeadline callback из inbox. Не ускоряйте это прямой правкой времени или статуса в live-БД. Для короткого показа используйте заранее начатые демо-дела либо покажите локальные тесты и пометьте live outcome как не проверенный.

Автоматическая локальная опора для обеих развилок:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://localhost/dom_domych_test_z_g3 \
  uv run pytest -q tests/infrastructure/test_g3_runtime.py tests/entrypoints/test_zamira_operator.py
```

Сохраняйте только обезличенное evidence: ID синтетического сценария, commit, времена UTC, счётчики карточки, исход дела и редактированные screenshots MAX web/mobile. Приватный реестр уведомлений проверяется отдельно по [`zamira-live-pdf-smoke.md`](zamira-live-pdf-smoke.md). Пока нет фактического просмотра в обоих клиентах и цельного live маршрута, G3 и Z14–Z16 остаются частично проверенными.
